# Requirements Document

## Introduction

This feature transitions the branch generation pipeline from "build" mode to "prove utility and control drift" mode. With the pipeline fully implemented (234 tests passing, 3 demo play states, end-to-end generation → evaluation → ranking), the next step is to freeze an official baseline, add semantic regression tests that validate tactical business behavior, measure generator diversity, instrument the pipeline with telemetry, and add an explainability layer so that every top-ranked branch carries a human-readable justification for its ranking.

The deliverables are: a benchmark manifest capturing expected behavior per scenario, semantic regression tests encoding tactical intentions, an analysis report script measuring generator diversity and pipeline health, pipeline telemetry per execution, and branch-level explanations on every ranked output.

## Glossary

- **Benchmark_Manifest**: A JSON file (`data/benchmark_manifest.json`) that records the official v1.0-baseline expectations for each demo scenario — expected top-K branch characteristics, score thresholds, and a snapshot of PipelineReport metadata.
- **Scenario**: A specific demo play state (e.g., `third_and_short_goal_line`, `second_and_long_after_sack`, `first_and_ten_midfield`) used as input to the pipeline.
- **Semantic_Regression_Test**: A test that validates expected tactical business behavior of the pipeline output, beyond structural correctness — e.g., that goal-line scenarios do not promote long-route branches.
- **Tactical_Intention**: A domain-level expectation about which branch families should dominate or be suppressed in a given Scenario, based on football knowledge.
- **Generator_Diversity_Report**: An analysis output measuring whether the three perturbation strategies (route, speed, decision) produce useful diversity or redundant noise.
- **Perturbation_Strategy**: One of the three branch generation methods: route_variation, speed_variation, or decision_variation (existing concept from Branch_Generator).
- **Pipeline_Telemetry**: Per-execution metrics capturing branches generated, hard-fail count, score-filtered count, average score by strategy, average score by scenario, and time per pipeline stage.
- **Branch_Explanation**: A human-readable annotation on a ranked branch describing why it rose or fell in ranking, which scoring block helped most, and which penalized most.
- **Pipeline_Report**: The structured JSON output of the pipeline containing ranked branches, evaluation reports, and metadata (existing model at `src/models/pipeline_report.py`).
- **Evaluation_Report**: The per-branch scoring output containing validity_score, opportunity_score, gating_flags, explanations, and sub_metrics (existing model at `src/models/evaluation_report.py`).
- **Top_K**: The set of highest-ranked branches returned by the pipeline after composite score ranking and filtering.
- **Entropy**: Shannon entropy computed over the distribution of a categorical variable (e.g., strategy labels in Top_K), measuring diversity. Higher entropy means more uniform distribution.
- **Strategy_Dominance**: The percentage of Top_K branches originating from a single Perturbation_Strategy. Values above 80% indicate generator bias.

## Requirements

### Requirement 1: Benchmark Manifest — Baseline Snapshot

**User Story:** As a pipeline maintainer, I want an official benchmark manifest that captures expected pipeline behavior per scenario, so that I can detect ranking degradation or output instability across code changes.

#### Acceptance Criteria

1. THE project SHALL include a `data/benchmark_manifest.json` file containing baseline expectations for each of the 3 demo Scenarios.
2. FOR EACH Scenario entry in the Benchmark_Manifest, THE entry SHALL contain: the scenario file name, the expected number of branches passing gating, the expected minimum composite score for the top-ranked branch, the expected maximum composite score for the bottom-ranked branch in Top_K, and a snapshot of strategy_counts from the Pipeline_Report metadata.
3. FOR EACH Scenario entry in the Benchmark_Manifest, THE entry SHALL contain an `expected_top_k` list recording the branch_ids and composite_scores of the Top_K branches produced by the pipeline with default configuration (N=20, K=5, seed=42).
4. THE Benchmark_Manifest SHALL contain a `pipeline_config` section recording the exact PipelineConfig used to generate the baseline (n, k, seed, validity_weight, opportunity_weight).
5. THE Benchmark_Manifest SHALL contain a `version` field set to `"v1.0-baseline"`.
6. THE Benchmark_Manifest SHALL be generated by a script (`scripts/generate_baseline.py`) that runs the pipeline on all 3 demo Scenarios and writes the manifest file.

### Requirement 2: Benchmark Manifest — Regression Detection

**User Story:** As a pipeline maintainer, I want automated tests that compare current pipeline output against the benchmark manifest, so that I am alerted when rankings or scores drift beyond acceptable thresholds.

#### Acceptance Criteria

1. WHEN the pipeline is run on a Scenario from the Benchmark_Manifest with the same PipelineConfig, THE regression test SHALL verify that the number of branches passing gating is within ±2 of the baseline expectation.
2. WHEN the pipeline is run on a Scenario from the Benchmark_Manifest with the same PipelineConfig, THE regression test SHALL verify that the top-ranked branch's composite score is within ±0.05 of the baseline expectation.
3. WHEN the pipeline is run on a Scenario from the Benchmark_Manifest with the same PipelineConfig, THE regression test SHALL verify that the set of Top_K branch_ids matches the baseline set exactly (same branches, same order).
4. IF a regression test detects a deviation beyond the allowed threshold, THEN THE test SHALL produce a descriptive failure message identifying the Scenario, the expected value, the actual value, and the metric that drifted.

### Requirement 3: Semantic Regression Tests — Goal-Line Behavior

**User Story:** As a pipeline maintainer, I want tests that validate tactical intentions for goal-line scenarios, so that I can ensure the pipeline promotes short-yardage branches and suppresses long-route branches near the end zone.

#### Acceptance Criteria

1. WHEN the pipeline processes the `third_and_short_goal_line` Scenario, THE semantic regression test SHALL verify that no branch in Top_K has a majority of player positions projecting more than 15 yards downfield from the line of scrimmage.
2. WHEN the pipeline processes the `third_and_short_goal_line` Scenario, THE semantic regression test SHALL verify that at least one branch in Top_K uses the decision_variation strategy (representing run/short-pass alternatives).
3. WHEN the pipeline processes the `third_and_short_goal_line` Scenario, THE semantic regression test SHALL verify that the average composite score of Top_K branches is above 0.3.

### Requirement 4: Semantic Regression Tests — Long-Yardage Recovery Behavior

**User Story:** As a pipeline maintainer, I want tests that validate tactical intentions for long-yardage recovery scenarios, so that I can ensure the pipeline promotes recovery branches and suppresses ultra-conservative or absurd calls.

#### Acceptance Criteria

1. WHEN the pipeline processes the `second_and_long_after_sack` Scenario, THE semantic regression test SHALL verify that at least one branch in Top_K uses the route_variation strategy (representing downfield passing options for yardage recovery).
2. WHEN the pipeline processes the `second_and_long_after_sack` Scenario, THE semantic regression test SHALL verify that no branch in Top_K has all player positions within 2 yards of their starting positions (ultra-conservative stagnation).
3. WHEN the pipeline processes the `second_and_long_after_sack` Scenario, THE semantic regression test SHALL verify that the average composite score of Top_K branches is above 0.25.

### Requirement 5: Semantic Regression Tests — Physical Failure Rejection

**User Story:** As a pipeline maintainer, I want tests that validate the pipeline never promotes branches with severe physical failures, so that I can trust the ranking reflects plausible outcomes.

#### Acceptance Criteria

1. FOR EACH of the 3 demo Scenarios, THE semantic regression test SHALL verify that no branch in Top_K has `passed_gating` set to False in its Evaluation_Report.
2. FOR EACH of the 3 demo Scenarios, THE semantic regression test SHALL verify that no branch in Top_K has a validity_score below 0.2.
3. FOR EACH of the 3 demo Scenarios, THE semantic regression test SHALL verify that every branch that failed gating has at least one entry in its Evaluation_Report `explanations` list describing the failure reason.

### Requirement 6: Generator Diversity Metrics

**User Story:** As a pipeline maintainer, I want to measure whether the three perturbation strategies produce useful diversity or just noise, so that I can identify generator bias and improve branch quality.

#### Acceptance Criteria

1. THE Generator_Diversity_Report SHALL compute, for each Scenario: unique branch count passing gating, distribution of branches by Perturbation_Strategy, percentage of generated branches discarded by the pipeline (failed gating or below validity threshold), Entropy of strategy labels in Top_K, and Strategy_Dominance percentage for Top_K.
2. THE Generator_Diversity_Report SHALL flag a warning when Strategy_Dominance in Top_K exceeds 80% for any Scenario.
3. THE Generator_Diversity_Report SHALL compute the average composite score per Perturbation_Strategy across all evaluated branches for each Scenario.
4. THE Generator_Diversity_Report SHALL be produced by a script (`scripts/analyze_diversity.py`) that runs the pipeline on all 3 demo Scenarios and outputs the report to stdout in a human-readable table format.

### Requirement 7: Pipeline Telemetry

**User Story:** As a pipeline maintainer, I want per-execution telemetry capturing key pipeline health metrics, so that I can identify bottlenecks and track pipeline behavior over time.

#### Acceptance Criteria

1. WHEN the pipeline completes execution, THE Pipeline_Report metadata SHALL contain a `telemetry` dict with the following keys: `branches_generated` (int), `hard_fail_count` (int — branches that failed gating), `score_filtered_count` (int — branches that passed gating but fell below validity threshold), `avg_score_by_strategy` (dict mapping strategy name to average composite score), `avg_score_by_scenario` (string identifying the scenario, included when scenario metadata is available), and `time_per_stage` (dict mapping stage name to elapsed seconds).
2. THE `time_per_stage` dict SHALL contain at minimum the keys: `generation`, `evaluation`, `ranking`, representing the wall-clock time spent in each pipeline stage.
3. THE `hard_fail_count` plus `score_filtered_count` plus the count of branches in `ranked_branches` plus branches that passed gating but were not in Top_K SHALL equal `branches_generated`.
4. THE telemetry data SHALL be JSON-serializable and included in the Pipeline_Report's `to_dict()` output without requiring schema changes to the existing Pipeline_Report dataclass.

### Requirement 8: Branch Explainability — Ranking Justification

**User Story:** As a pipeline user, I want every top-ranked branch to carry a human-readable explanation of why it was ranked where it is, so that I can trust and understand the pipeline's decisions.

#### Acceptance Criteria

1. FOR EACH branch in the Top_K of a Pipeline_Report, THE Pipeline_Orchestrator SHALL include a `ranking_explanation` dict in the branch's entry within `ranked_branches`.
2. THE `ranking_explanation` dict SHALL contain: `promoted_factors` (list of strings describing scoring dimensions that contributed positively), `penalized_factors` (list of strings describing scoring dimensions that penalized the branch), `top_scoring_block` (string identifying the sub-metric with the highest normalized contribution), and `bottom_scoring_block` (string identifying the sub-metric with the lowest normalized contribution).
3. WHEN a branch has a validity_score above 0.7, THE `promoted_factors` list SHALL include a reference to the specific plausibility or fidelity sub-metric that scored highest.
4. WHEN a branch has an opportunity_score below 0.4, THE `penalized_factors` list SHALL include a reference to the specific tactical or decision sub-metric that scored lowest.
5. IF a branch was close to being filtered (validity_score within 0.1 of the validity threshold), THEN THE `ranking_explanation` SHALL include a `near_threshold_warning` string explaining the proximity to the filter boundary.

### Requirement 9: Branch Explainability — Filtered Branch Reasons

**User Story:** As a pipeline user, I want branches that were filtered out to carry an explanation of why they were removed, so that I can understand what the pipeline rejected and why.

#### Acceptance Criteria

1. FOR EACH branch that failed gating, THE Pipeline_Report `evaluated_branches` entry SHALL contain a `filter_reason` string starting with "Rejected: " followed by the gating failure explanation.
2. FOR EACH branch that passed gating but fell below the validity threshold, THE Pipeline_Report `evaluated_branches` entry SHALL contain a `filter_reason` string starting with "Filtered: " followed by a description of which validity sub-scores were insufficient.
3. THE `filter_reason` field SHALL be present only on branches that were not included in the Top_K ranked list.

### Requirement 10: Analysis Report Script

**User Story:** As a pipeline maintainer, I want a single script that produces a comprehensive analysis report covering generator diversity, fail rates by strategy, and top-K composition by scenario, so that I can assess pipeline health at a glance.

#### Acceptance Criteria

1. THE project SHALL include a script (`scripts/analyze_diversity.py`) that runs the pipeline on all 3 demo Scenarios with default configuration and produces a consolidated report.
2. THE analysis report SHALL include, for each Scenario: a summary table of Top_K branches with branch_id, composite_score, strategy, and validity_score; a strategy distribution table showing branch count and average score per Perturbation_Strategy; the discard rate (percentage of branches not in Top_K); and the Strategy_Dominance and Entropy metrics for Top_K.
3. THE analysis report SHALL include a cross-scenario summary showing overall strategy balance, overall discard rate, and any Scenarios where Strategy_Dominance exceeds 80%.
4. THE script SHALL exit with code 0 on success and code 1 if any Scenario fails to produce a valid Pipeline_Report.

### Requirement 11: Baseline Generation Script

**User Story:** As a pipeline maintainer, I want a script that generates the benchmark manifest from current pipeline output, so that I can re-baseline after intentional changes.

#### Acceptance Criteria

1. THE project SHALL include a script (`scripts/generate_baseline.py`) that runs the pipeline on all 3 demo Scenarios with default configuration and writes `data/benchmark_manifest.json`.
2. WHEN the script completes, THE generated Benchmark_Manifest SHALL conform to the structure defined in Requirement 1.
3. THE script SHALL print a summary to stdout showing, for each Scenario: the number of branches passing gating, the top-ranked branch_id and composite_score, and the strategy distribution.
4. THE script SHALL exit with code 0 on success and code 1 if any Scenario fails to produce a valid Pipeline_Report.

### Requirement 12: Semantic Regression Test File

**User Story:** As a pipeline maintainer, I want all semantic regression tests in a single, well-organized test file, so that I can run them as part of the standard test suite.

#### Acceptance Criteria

1. THE project SHALL include a test file `tests/test_semantic_regression.py` containing all semantic regression tests defined in Requirements 3, 4, and 5.
2. THE test file SHALL use `pytest` fixtures to load demo play states and run the pipeline once per Scenario, reusing the Pipeline_Report across multiple assertions within the same Scenario.
3. THE test file SHALL use descriptive test names that encode the tactical intention being validated (e.g., `test_goal_line_no_long_routes_in_top_k`).
4. WHEN a semantic regression test fails, THE failure message SHALL describe the tactical expectation that was violated and the actual pipeline output that caused the failure.

### Requirement 13: Parse and Print Benchmark Manifest JSON

**User Story:** As a pipeline maintainer, I want to reliably load and save the benchmark manifest, so that scripts and tests can share the same baseline data.

#### Acceptance Criteria

1. WHEN a valid `benchmark_manifest.json` file is provided, THE manifest loader SHALL parse it into a structured dict with validated keys for `version`, `pipeline_config`, and `scenarios`.
2. WHEN the manifest file is missing or contains invalid JSON, THE manifest loader SHALL raise a descriptive error identifying the problem.
3. THE manifest printer SHALL produce a JSON-serializable dict from the structured manifest data.
4. FOR ALL valid Benchmark_Manifest dicts, loading the printed output SHALL produce an equivalent dict (round-trip property).
